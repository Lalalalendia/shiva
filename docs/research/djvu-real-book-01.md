# SHIVA-DJVU-REAL-BOOK-01 — private full-source raster QA

**Accepted locally on 2026-10-22, not production.** The real 378-page
DjVu supplied by the user was held only in the model's private working
container. No DjVu bytes, raster pixels, page text, or OCR output went
to GitHub or Notion.

The ready-made **djvu-rs 0.43.0 (MIT)** decoder successfully rendered
**378/378 pages at 300 DPI**, in 20-page batches using fresh child
processes. The original SHA-256 was unchanged. Median render time =
**0.2127 s/page**, P95 = **0.326 s**, maximum = **0.6877 s**,
maximum sampled worker RSS = **307.1 MiB**, wall time **111.25 s**.
All 378 pages had nonwhite pixels. This establishes read/render success
on **this book**; it does not establish full pixel fidelity or OCR
correctness. Its 600 DPI full-compositor images and legacy 1-bit JB2
masks are not interchangeable oracles.

## Page 256 root cause

A Go-board diagram dominates the page. On that page the two Tesseract
fast OCR passes produce **identical 415 normalized characters of
real paragraph text**. Their previous 15% full-page string mismatch
comes from false OCR of diagram pieces, not paragraph loss.
Tesseract TSV confidence on this page: in the diagram region 36 words,
mean **38.3** (median 37.5); in true paragraph region 52 words,
mean **96.2** (median 96.5). The diagram-region garbage prefix
is 106 vs 86 normalized characters between the two runs.

Implication: Shiva needs *raw* page/bbox/confidence OCR receipts separate
from filtered search text. Do not blindly discard all low-confidence
tokens, misclassify figures as text, or mark an arbitrary scan Complete.
Per-page extraction should be Partial / Needs review when uncertain.

## Reproduce locally only

The QA-only script `scripts/ci/private_djvu_render_audit.py` takes an
**explicit authorized local source**, expected SHA-256 and page count.
It restarts a worker after each batch and exports JSON *metrics only*.
Example:

```sh
python scripts/ci/private_djvu_render_audit.py \
  --source /private/book.djvu --expected-sha256 YOUR_SHA256 \
  --expected-pages 378 --dpi 300 --batch-pages 20 \
  --out /private/metrics.json
```

The GitHub Actions gate uses *only four authored synthetic pages*
already generated by `ready_ocr_lab.py` to test this helper, never the
user-supplied book. No model training or re-training occurs.

Important limits: resident memory is sampled, **not enforced by OS**;
per-page duration checked after render, hard termination is the outer
per-batch process timeout. No CPU/RAM sandbox is proven here. Actual
production Shiva worker needs OS-enforced resource caps and File Gate
immutable authorized snapshots. The current Linux proof-of-concept
worker-client has a 2 MiB input cap (the sample book is 5.58 MB), so
that separate blocker cannot simply be ignored.
